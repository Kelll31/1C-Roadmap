## 1. Эволюция технологической платформы

Мажорные релизы 8.3.25, 8.3.26, 8.3.27 и концептуально новый интерфейс 8.5 демонстрируют стратегический фокус вендора на **абсолютную отказоустойчивость**, оптимизацию работы с экстраординарными объёмами данных и создание бесшовного пользовательского опыта.

### 1.1 Архитектура кластера и управление HighLoad-средами

**Балансировка нагрузки.** Новая архитектура обеспечивает автоматическое перераспределение задач между узлами кластера на основе доступности серверов и анализа производительности в реальном времени. Появилась тонкая настройка лимитов RAM для `rphost`-процессов, что критически повышает отказоустойчивость при ресурсоёмких пользовательских запросах.

**Сессионные данные.** Реализована возможность хранить служебные данные кластера в нескольких независимых каталогах — устраняет исторический bottleneck при высоких нагрузках на дисковую подсистему. Параметры разрыва соединений настраиваются «на лету» без перезапуска кластера.

**Infrastructure as Code.** Настройки кластера можно экспортировать в файл и импортировать — необходимое условие для воспроизводимого развёртывания тестовых и продуктивных сред.

**Фоновая реструктуризация БД.** Ключевое нововведение для систем 24/7: обновление конфигурации больше не требует монопольного отключения пользователей на весь период реструктуризации таблиц. Процесс инкрементален: автоматически приостанавливается в часы пиковой нагрузки и возобновляется в период минимальной активности.

### 1.2 Оптимизация СУБД и хранение данных

**Копии баз данных.** Обновление аналитических копий выполняется параллельно через асинхронные фоновые задания. Встроена защита от ошибочного использования одной физической БД несколькими копиями. При некритичном исключении в тяжёлом аналитическом запросе копия больше не отключается от кластера.

**Блочное хранение двоичных данных.** Вложенные файлы, сканы и мультимедиа теперь хранятся блочно непосредственно в информационной базе (клиент-серверный вариант), преодолевая системные ограничения на размер файлов. Реализовано параллельное сохранение в хранилище платформы и в СУБД — при сбое хранилища операции не прерываются, платформа переключается на СУБД.

**Форматы архивов.** На уровне встроенного языка (BSL) реализована нативная работа с архивами GZIP, RAR, 7-ZIP, XZ, TAR — без COM-объектов и системных вызовов.

**Производительность СУБД.** Достигнуто ускорение операций чтения/записи для Microsoft SQL Server и PostgreSQL; ускорено первоначальное наполнение копии БД.

### 1.3 Система взаимодействия и пользовательский опыт

**Масштабируемость СВ.** Максимальное количество участников одного обсуждения расширено до 3000 пользователей. Webhook поддерживает передачу произвольных данных — открывает возможности для двусторонней интеграции с внешними ИТ-системами.

**Видеосвязь.** Адаптивное регулирование громкости, агрессивное эхоподавление и интеллектуальное шумоподавление. Нагрузка на CPU клиента при групповых звонках остаётся константной (не растёт с числом участников). Поддержка ссылок-приглашений для внешних участников без учётной записи 1С.

**Уведомления клиента (Client Notifications API).** Ключевой архитектурный паттерн: вместо поллинга по таймеру сервер отправляет push-уведомление напрямую в конкретный клиентский сеанс по завершении длительной операции. Радикально снижает паразитную нагрузку на СУБД и кластер.

**Интерфейс 8.5.** Концептуальное развитие парадигмы «Такси»:
- Полный переход от растровых изображений к **SVG-иконкам** — абсолютная чёткость на High-DPI мониторах
- **Безмодальный режим** — устраняет блокировку потока в веб-браузерах; обязателен для веб-клиента и мобильных устройств
- Компактный режим форм для опытных пользователей (максимальная плотность информации)
- Гибридный режим миграции: конфигурации можно запускать в классическом интерфейсе, новом или смешанном
- Полная поддержка доступности (a11y) для незрячих пользователей (NVDA, горячие клавиши)

## 2. Информационная безопасность

### 2.1 Криптографические алгоритмы и защита паролей

Платформа перешла от уязвимого SHA-1 к современным алгоритмам:

| Алгоритм | Стойкость | Примечание |
|---|---|---|
| **PBKDF2-HMAC-SHA256** | Максимальная | Рекомендован. Соль + итерации делают GPU-брутфорс нецелесообразным |
| **SHA-512** | Высокая | Альтернативный вариант |
| **SHA-256** | Высокая | Базовый современный вариант |
| ~~SHA-1~~ | ❌ Уязвим | Устарел, не использовать |

> ⚠️ **Необратимость:** Переход на любой алгоритм, отличный от SHA-1, **жёстко привязывает базу к платформе 8.3.26+**. Даунгрейд невозможен. Всегда создавайте резервную копию перед тестированием новых релизов.

**Проактивная защита паролей.** Реализована проверка нового пароля по трём уровням:
1. Встроенный словарь слабых паролей платформы
2. Корпоративный список недопустимых комбинаций (загружается из файла)
3. Внешние API (аналог Have I Been Pwned) — при наличии интернет-доступа

### 2.2 Аутентификация и контроль сеансов

| Механизм | Описание | Бизнес-ценность |
|---|---|---|
| **QR-код (беспарольный вход)** | Смартфон как аппаратный токен. Сканирование QR → криптографический токен → сессия на десктопе. | Защита от кейлоггеров и shoulder surfing в публичных местах |
| **Idle Timeout** | Принудительное завершение сеанса после периода бездействия | Соответствие ISO 27001; освобождение лицензий |
| **ЕСИА v3.34** | Интеграция с Единой системой идентификации | Бесшовная работа с государственными ИС |
| **OpenID Connect** | Стандартный федеративный вход | Корпоративные SSO-системы |

**Расширенное логирование безопасности.** Технологический журнал и журнал регистрации теперь детально фиксируют: административные действия, изменения прав доступа в ролях, состав изменённых объектов метаданных. Все протоколы по умолчанию работают поверх SSL с проверкой сертификатов.

> 💡 **Для разработчика:** Помните об Idle Timeout при разработке длительных обработок. Запускайте тяжёлые операции через **Фоновые задания** (`ФоновыеЗадания.Выполнить()`), а статус передавайте через Client Notifications API — не через интерактивный клиентский сеанс.

## 3. Архитектурная парадигма

### 3.1 Две платформы — два назначения

Важнейший стратегический тренд 2026 года: «1С:Предприятие 8» и «1С:Элемент» — **не конкуренты**, а взаимодополняющие инструменты для разных задач.

| Критерий | 1С:Предприятие 8.x / 8.5 | 1С:Элемент |
|---|---|---|
| **Топология** | Централизованная (монолитная), транзакционная | Распределённая, микросервисная, асинхронная |
| **UI-стек** | Управляемые формы, декларативный BSL | HTML / CSS / JavaScript, кастомный дизайн |
| **Язык логики** | BSL (встроенный язык 1С) | Новый язык 1С:Элемент (строгая типизация, асинхронность) |
| **Развёртывание** | On-premise / выделенное облако | Cloud-native, контейнеры, горизонтальное масштабирование |
| **Кросс-платформенность** | Адаптированная (Linux, macOS, Windows) | Нативная (Linux, Windows, macOS; x86 и ARM) |
| **Идеальные сценарии** | ERP, бухучёт, ЗУП, производство, АСУ ТП | Личные кабинеты B2C/B2B, маркетплейсы, корпоративные порталы |
| **Пользователи** | Внутренние (сотрудники, бухгалтеры) | Внешние (клиенты, партнёры, дилеры — тысячи одновременно) |

### 3.2 Гибридный ландшафт: стратегия Enterprise-2026

Наиболее эффективная стратегия крупных корпораций:

```
┌─────────────────────────────┐     REST API / 1С:Шина     ┌──────────────────────────┐
│   1С:ERP (Back-office)      │ ←────────────────────────→ │  1С:Элемент (Front-office)│
│   Единый источник истины    │                             │  B2C-витрина / кабинет   │
│   Финансы, производство,    │                             │  Тысячи внешних         │
│   ЗУП, транзакции           │                             │  пользователей          │
└─────────────────────────────┘                             └──────────────────────────┘
```

**Почему это работает:**
- Запуск тысяч внешних пользователей напрямую в 1С:ERP = огромные затраты на лицензии + непредсказуемая нагрузка на транзакционный сервер
- 1С:Элемент масштабируется горизонтально средствами веб-серверов, выдерживает пики нагрузки (распродажи)
- Обращение к 1С:ERP только в момент необходимости фиксации транзакции (создание заказа, проверка остатков)

**Для разработчика:** Освоение 1С:Элемент требует серьёзного переобучения — основы веб-архитектуры, асинхронное программирование, новый серверный синтаксис. Это задача уровня Senior+, не Junior.

## 4. DevOps, CI/CD и качество

### 4.1 Трансформация: от Конфигуратора к 1С:EDT + Git

```
Конфигуратор (монолитный CF-файл)
        ↓
1С:EDT (файловая структура метаданных) + Git
        ↓
Pull Requests → Code Review → CI Pipeline
        ↓
Автосборка → SonarQube (BSL) → BDD-тесты → Деплой
```

**1С:EDT** — IDE на базе Eclipse с нативной двусторонней интеграцией с Git. Позволяет командам 1С внедрить:
- Изолированное ветвление функционала (branching)
- Формализованные Pull/Merge Requests
- Обязательное Code Review перед слиянием в основную ветку
- Интеграцию с Jenkins / GitLab CI / GitHub Actions

**Ключевые инструменты DevOps-экосистемы:**

| Инструмент | Назначение |
|---|---|
| `gitsync` | Синхронизация конфигурации (CF/EDT) ↔ Git-репозиторий |
| `deployka` | Деплой конфигураций и расширений в CI/CD |
| `1cca` | Командная строка для работы с конфигурациями |
| `bsp-tools` | Утилиты для работы с БСП |
| `oscript-library` | Библиотеки OneScript для автоматизации |
| BSL Language Server | Статический анализ BSL. База для SonarQube-плагина |
| SonarQube BSL Plugin | Интеграция анализа BSL-кода в SonarQube |

### 4.2 Behavior-Driven Development: Vanessa Automation

Индустриальный стандарт тестирования 1С в 2026 году — не UI-рекордеры (хрупкие, нечитаемые), а BDD-фреймворк **Vanessa Automation** с языком **TurboGherkin**.

**Архитектурное разделение:**

```
Бизнес-аналитик (Vanessa ADD):           Разработчик:
┌─────────────────────────────┐          ┌─────────────────────────────┐
│ scenario.feature            │          │ steps_library.bsl           │
│                             │   ────→  │                             │
│ Допустим: клиент имеет      │          │ // &Шаг("клиент имеет       │
│   просроченный долг         │          │ //   просроченный долг")    │
│ Когда: менеджер проводит    │          │ Процедура ШагКлиентДолг()   │
│   заказ клиента             │          │   ПроверитьДолгКлиента();   │
│ Тогда: система блокирует    │          │ КонецПроцедуры              │
│   проведение                │          └─────────────────────────────┘
└─────────────────────────────┘
```

**Преимущества:**
- Сценарий одновременно является **живой документацией** и **техническим заданием**
- Изменение UI (кнопка переехала) не ломает сценарий — только один программный шаг
- Тесты хранятся в Git вместе с кодом, автоматически запускаются в CI

## 5. Искусственный интеллект

### 5.1 Model Context Protocol (MCP) и оркестрация тестирования

MCP — протокол, позволяющий LLM (Claude, ChatGPT, Gemini) напрямую и безопасно взаимодействовать с локальными инструментами разработчика.

**MCP-сервер `spremotely-vanessa-app-mcp`** — мост между AI-агентом и Vanessa Automation:

| Команда MCP | Что делает AI |
|---|---|
| `create_feature` | Читает описание задачи (Jira/ТЗ) → генерирует `.feature`-файл на TurboGherkin |
| `parse_feature` | Валидирует логику BDD-сценария |
| `generate_steps` | Создаёт шаблоны шагов на BSL для новых действий |
| `run_scenario` | Запускает тесты → анализирует лог → предлагает исправление |

Результат: время на создание исчерпывающего покрытия автотестами сокращается на порядки.

### 5.2 AI-ориентированные среды разработки

**Cursor IDE** — AI-первый редактор, вытесняющий классические IDE. Пакет `1c-ai-development-kit`:
- Правила, агенты и скиллы, обученные синтаксису BSL и архитектуре метаданных 1С
- Контекстный рефакторинг целых процедур по команде на естественном языке
- Оркестрация через MiniMax M2 — анализ структуры БД + переписывание кода с временными таблицами и пакетными запросами

**Пример рабочего процесса:**
```
Разработчик: "Оптимизируй этот запрос — убери запрос из цикла, перенеси
              выполнение на сервер с передачей массива ссылок"

AI-агент:    1. Анализирует структуру регистров в метаданных
             2. Формирует пакетный запрос с ВТ (временные таблицы)
             3. Переносит вызов на &НаСервереБезКонтекста
             4. Возвращает production-ready код
```

**1С:Напарник** — официальный AI-ассистент для конечных пользователей: формирование отчётов и поиск документов через текстовый/голосовой запрос на естественном языке.

> ⚠️ **Безопасность данных:** Никогда не передавайте реальный коммерческий код в публичные LLM. Для анализа продуктивных баз — только локальные модели (Ollama) или корпоративные защищённые аккаунты.

## 6. Налоговая реформа 2026

### 6.1 Ключевые законодательные изменения

| Изменение | Влияние на 1С-системы |
|---|---|
| **НДС 22%** | Пересчёт алгоритмов ценообразования, взаиморасчётов, проводок, ФР |
| **Новые лимиты УСН/ОСНО** | Многие средние компании экстренно переходят на ОСНО |
| **Расширение маркировки «Честный ЗНАК»** | Новые категории: одежда (4-я волна), радиоэлектроника, меховые изделия |
| **МЧД (Машиночитаемые доверенности)** | Обязательное поле «Должность»; блокировка без ИНН представителя |
| **Удалённый выпуск КЭП** | Через «Госключ» — без физического посещения УЦ |

### 6.2 Парадигма безопасных обновлений

Агрессивная законодательная среда означает одно: **способность системы быстро принимать обновления вендора — вопрос выживания бизнеса.**

Главная проблема — «грязный код»: ручные правки типовых программных модулей. Обновление такой базы превращается в многодневный ручной мёрдж с высоким риском ошибок при выгрузке отчётности.

**Правильная архитектура 2026:**

```
Типовая конфигурация (поддержка вендора)
├── Расширение конфигурации          ← Все доработки ЗДЕСЬ
│   ├── &Вместо / &После / &Перед
│   └── Подписки на события (БСП)
├── Внешние отчёты и обработки
└── БСП-механизмы переопределения
```

**Процедура безопасного обновления (DevOps-чеклист):**
1. Резервный архив продуктивной базы
2. Автоматическое развёртывание тестовой копии
3. Накат обновления от вендора
4. Запуск регрессионных BDD-тестов (выгрузка в ЭДО, банкинг, ФНС-форматы)
5. Только при успешных тестах → применение на продуктиве

## 7. Матрица компетенций

Подробная матрица — в [03_Competencies.md](03_Competencies.md). Здесь — архитектурный обзор четырёх специализированных треков.

### 7.1 Трек «Разработка» (Junior → Middle → Senior)

**Junior** (0–6 мес.): объектная модель платформы, BSL, язык запросов, немодальные формы, Git. Сертификат: **1С:Профессионал**.

**Middle** (1–2 года): расширения, БСП, HTTP-сервисы REST/SOAP, XDTO, BDD/Vanessa, управляемые блокировки, RLS, Linux, AI-инструменты. Сертификат: **1С:Специалист**.

**Senior/Architect** (3–5 лет): гибридные ландшафты (ERP + Элемент), 1С:Шина, брокеры сообщений, CI/CD-пайплайны, SonarQube, менторство, мобильная платформа.

### 7.2 Трек «Архитектор»

Проектирование отказоустойчивых кластеров 1С, балансировка нагрузки, выбор между синхронными HTTP-вызовами и асинхронными очередями (RabbitMQ, Kafka, 1С:Шина). Управление технического долгом через EDT. Инфраструктура — VMware/VirtualBox, облако (Selectel, 1С-ГРМ). Требования к рабочей станции: i5+, SSD, 16 ГБ RAM.

### 7.3 Трек «1С:Эксперт по технологическим вопросам»

Узкоспециализированная роль: не пишет функционал, **расследует падение производительности** в HighLoad-системах (тысячи одновременных пользователей).

Ключевые компетенции:
- PostgreSQL (Linux) + MS SQL Server: планы запросов, индексы, `EXPLAIN ANALYZE`
- Linux CLI: `bash`, `grep`, `awk`, `sed` — анализ Технологического журнала
- Дедлоки: расследование, оптимизация логики транзакций
- Нагрузочное тестирование: **«Тест-Центр» из 1С:КИП**
- Кластер 1С: фоновая реструктуризация БД, IaC-экспорт настроек

Сертификат: **1С:Эксперт по ТВ** (многодневная защита практического кейса перед комиссией).

### 7.4 Трек «Бизнес-аналитик / Консультант ERP»

Связующее звено бизнес ↔ разработка. Глубокое знание 1С:ERP, 1С:ЗУП, 1С:УХ — производство, МСФО, казначейство, P&L. Виртуозная СКД в пользовательском режиме. TurboGherkin-сценарии через Vanessa ADD. 1С:СППР — визуальное моделирование архитектуры предприятия.

## 8. Мобильная экосистема

### 8.1 Нативные приложения и offline-режим

Мобильная платформа 1С компилирует единую BSL-кодовую базу в нативные приложения для **Android и iOS**. Ключевая особенность — **offline-режим**: полный массив данных хранится на устройстве, обмен с центральной базой происходит асинхронно при появлении сети.

Доступные аппаратные интеграции:
- GPS/ГЛОНАСС — геолокация
- Камера — сканирование штрихкодов и фотофиксация
- Мультимедиа — запись аудио/видео
- Системные интеграции — адресная книга, календарь, SMS/Email

### 8.2 B2C-монетизация

Стратегическое нововведение: нативная поддержка **In-App Billing** через Apple In-App Purchase и Google Play. Это позволяет создавать **коммерческие монетизируемые приложения** для массового рынка (мобильные витрины с платной подпиской) инструментами 1С-разработчика. Поддержка рекламных интеграторов (iAd, AdMob).

## Заключение

Экосистема «1С:Предприятие» в 2026 году совершила качественный скачок от закрытой учётной среды к **сложнейшему Enterprise-инженерному контуру**, работающему по мировым стандартам.

**Ключевые выводы:**

| Тенденция | Значение для разработчика |
|---|---|
| Архитектурное расслоение (1С:Предприятие + 1С:Элемент) | Нужно уметь выбирать инструмент под задачу |
| BDD + CI/CD как стандарт | «Накатить руками» — больше не профессионально |
| Расширения вместо «грязного кода» | Архитектурная гигиена = выживание бизнеса при реформах |
| PBKDF2, Idle Timeout, QR-вход | Безопасность — не опция, а базовое требование |
| AI-агенты (MCP, Cursor) | Высвобождают время для архитектуры; не заменяют знания |
| НДС 22%, маркировка, МЧД | Бизнес-контекст — обязательное знание разработчика |

Дорожная карта специалиста — путь от базового синтаксиса BSL к **проектированию отказоустойчивой инфраструктуры**, оптимизации СУБД, глубокому анализу бизнес-процессов и работе с AI-инструментами нового поколения.
